# ESDB ORM architecture

Status: implemented v1 architecture plus explicitly marked future extensions. The live tree now contains
the Drizzle frontend (`orm/drizzle/`), normative IR v1 contract (`orm/ir/`), reference compiler and
migration packager (`tools/esdb-schema/`), generated C++/TypeScript/ES3/ESABI surfaces, an executable User
vertical slice, and ORM CI/tests. This document records both the implemented contract and the remaining
architecture targets. Field-level behavior defers to `orm/ir/esdb-ir-v1.md` and
`tools/esdb-schema/`.

Scope: `esdb/` only. Statements that remain future work are marked `ASSUMPTION:`, `PROVISIONAL:`, or
`TARGET:`. The implemented IR v1 covers `integer`/`text`/`real`/`blob` columns, multi-table
schema structure, FKs/CHECKs/explicit indexes, deterministic INNER/LEFT joins, CRUD + upsert queries,
keyed mutations, deterministic logical/physical naming, packaged incremental Drizzle Kit migration
history, SQLite-semantic physical-schema hashing/differential, and explicit adoption baselines/reports.

## 2. Goals and non-goals

### 2.1 Goals

1. **Static correctness.** Schema, queries, and row mapping are compiled. Type errors, missing columns,
   wrong arity, and NULL mistakes are build failures, not runtime surprises.
2. **One schema, many runtimes.** A single IR v1 produces C++, TypeScript, ES3, and ESABI bridge
   artifacts with shared semantics and exact value handling.
3. **ESDB-native.** The ORM sits directly on ESDB Runtime: one `esdb_database`, ESDB transactions,
   ESDB migrations, the controlled SQLite escape hatch. No second database abstraction is introduced.
4. **Migration safety.** Migrations are packaged, hashed, linted, applied atomically through
   `esdb_migrate()`, and verified against the compiled schema at runtime.
5. **Determinism and reviewability.** Every generated byte is a pure function of (IR, generator version,
   options). SQL is visible in the repository and reviewable in diffs.
6. **No runtime ORM.** No reflection, no dynamic schema registry, no runtime SQL assembly, no lazy
   loading, no hidden queries.
7. **Adoption without rewrites.** An existing ESDB Runtime consumer (Workmark being the reference case)
   can adopt the ORM at a chosen schema version without changing its storage engine, its helper-process
   topology, or its Store non-dependency.

### 2.2 Non-goals

- A general-purpose runtime query builder or an ActiveRecord-style object graph.
- Multi-dialect SQL abstraction. The dialect is SQLite as pinned by ESDB. IR keeps a `dialect` field for
  future-proofing only.
- Replacing ESDB Store. Store remains the IndexedDB-shaped object/state layer; the ORM is the relational
  compiler, and ORM is not Store: it does not emulate named stores, revisions, or change polling. They
  share a database file only by explicit product choice, never by ORM dependency.
- Owning connection lifecycle. The application owns `esdb_open`/`esdb_close`; generated code borrows
  handles.
- Async, reactive, or background behavior. Pull-based, synchronous, application-driven.
- Runtime schema migration from ES3. ES3 never applies DDL.
- An ORM for arbitrary existing databases without a schema source. Reverse import is an explicit
  adoption tool (Phase 4), not a general introspection product.

## 3. Live ESDB constraints (observed)

These are read from the current tree and are binding on the ORM design.

### 3.1 Runtime

 - Version `0.2.0`, `ESDB_ABI_VERSION 2` (`include/esdb/esdb_types.h`).
- One SQLite connection per `esdb_database`; `ESDB_OPEN_FULLMUTEX` is the default. `FULLMUTEX` serializes
  individual SQLite calls but does not serialize an application-level `begin -> calls -> commit` sequence
  (`docs/ABI.md`).
- Durability policy is explicit: `journal_mode=MEMORY|OFF` and `synchronous=OFF` are rejected at open;
  requested pragmas are read back and must match exactly. Generated code must not change durability
  pragmas.
- Transactions and LIFO savepoints are the only sanctioned scopes. Savepoint names use
  `[A-Za-z0-9_]{1,64}`; the case-insensitive prefix `__esdb_` is reserved.
- `esdb_exec()` executes semicolon-separated SQL and is documented as intended for DDL, migrations, and
  product-owned schema management.
- `esdb_native_handle()` is the controlled escape hatch: a borrowed `sqlite3*`, valid only while the
  database is open, never to be closed, sharing the connection's transaction/locking/thread context.
  Mutating reserved `__esdb_` tables or durability pragmas through it invalidates ESDB assumptions.
  The matching pinned `sqlite3.h` is installed as `<esdb/sqlite3.h>`.
- ESDB builds SQLite with `SQLITE_THREADSAFE=1`, `SQLITE_DEFAULT_FOREIGN_KEYS=1`, `SQLITE_DQS=0`,
  `SQLITE_ENABLE_DBSTAT_VTAB=1`, `SQLITE_USE_URI=1`, plus optional `SQLITE_ENABLE_API_ARMOR`
  (`CMakeLists.txt`). `SQLITE_DQS=0` means generated SQL must never rely on double-quoted string
  literals; identifiers are double-quoted, values are always bound.
- Extension loading is not enabled by ESDB. Generated code must not call `sqlite3_load_extension()`.

### 3.2 Schema versioning and migrations

`esdb_migrate()` is the only supported migration driver:

- `PRAGMA user_version` is the product schema version slot.
- Migrations are contiguous single-step: each entry is `{from_version, to_version = from_version + 1}`.
- The whole run executes inside one `BEGIN IMMEDIATE` transaction; a missing step or failing callback
  rolls everything back and leaves `user_version` unchanged.
- Downgrades return `ESDB_ERR_UNSUPPORTED`; forward-only is explicit v0.1 policy.
- The callback runs inside the migration transaction and **must not** `BEGIN`, `COMMIT`, `ROLLBACK`, or
  otherwise take transaction control.

Consequences for the ORM:

1. One Drizzle Kit migration directory maps to exactly one ESDB step.
2. Migration SQL must be transaction-safe (see [§7.4](#74-migration-safety-lint)).
3. The ORM must not keep a second migration ledger. Kit's `__drizzle_migrations` journal is a build-time
   artifact; at runtime `user_version` plus the generated manifest is authoritative.

### 3.3 Store (explicitly out of scope)

Store is optional and separate: named stores, canonical values, durable revisions, change polling, and
reserved `__esdb_` tables (`__esdb_meta`, `__esdb_stores`, `__esdb_records`, `__esdb_object_changes`).

The public APIs are split: `esdb_object_store.h` / `esdb_object_store.cpp` implement durable SQLite-backed
ObjectStore, while `esdb_store.h` / `esdb_store.cpp` implement process-memory Store state. The ExternalObject
adapter exposes both `objectStore*` (durable) and `store*` (process-memory) method families. ORM depends
on neither API; `docs/STORE.md` describes their distinct lifetimes and semantics.

The ORM depends on **none** of it. The ORM's only surfaces are `esdb.h`, `esdb_types.h`, `esdb_value.h`,
`esdb.hpp`, and the `esdb_native_handle()` escape hatch. If those surfaces change during the Store
migration, the ORM is unaffected.

### 3.4 ExternalObject adapter / ES3

- ESABI 0.3.1 is the host ABI. The adapter is deliberately thin. Generated ORM operations use
  fixed named ESABI methods, while the generic ESDB facade also exposes the explicit bounded typed-SQL
  `querySql` escape hatch. SQL text and typed parameters are separate and values are always bound;
  there is no callback registration or asynchronous native call into JSX
  (`adapters/externalobject/esdb_externalobject_abi.h`).
- JS-visible handles are generation-tagged; stale tokens are rejected. One explicit transaction per
  adapter slot.
- The measured Adobe string lane cannot faithfully carry embedded U+0000 or all surrogate sequences, so
  the JSX facade transports byte-exact strings as ASCII hex and 64-bit integers/revisions as canonical
  decimal strings (`docs/ABI.md` "Byte-exact ES3 wire").
- `ESDB.unload()` refuses while database handles remain open; Adobe may keep the DLL mapped until process
  exit.

The ORM must not weaken any of these invariants, and must reuse the existing wire conventions instead of
inventing a second encoding.

### 3.5 Workmark compatibility (locked)

`docs/ARCHITECTURE.md` fixes the Workmark topology: `Workmark.aip -> VectorIPC -> workmark-helper ->
Workmark StorageWriter -> ESDB Runtime -> SQLite`. Workmark keeps its relational schema in its own tables
inside the helper and never uses Store. Therefore:

- The ORM must be usable with Runtime alone: no Store schema, no adapter, no ES3, no `__esdb_` tables.
- Generated C++ must link against `ESDB::esdb` and the installed `<esdb/sqlite3.h>` only.
- Adoption must be incremental: baseline an existing schema at version N, take ownership of N+1.. only,
  and never reinterpret or reset an existing migration ledger without an explicit operator action.

### 4.2 Decision

**Chosen:** Drizzle schema as the authoring frontend, consumed through a **version-pinned introspection
adapter**; stable drizzle-kit CLI as the DDL/diff generator of record; **IR v1** as the canonical semantic
model; generated static SQL and typed artifacts for C++, TypeScript, and (later) ES3.

**Challenged and rejected as the core:**

- Kysely is a better *runtime query builder* than Drizzle for modern TS, but it is not a schema-diff
  authority and its types are not a schema. It is retained as the **later modern-TS runtime adapter**
  ([§10](#10-modern-ts-strategy-kysely-adapter)), not as the source of truth.
- Prisma's schema language would put a second, non-TS source of truth in front of IR and drag engine
  binaries into the runtime path. It is rejected on architecture and weight, not on quality.
- sqlite_orm/sqlpp11/SOCI are C++-only runtime libraries; adopting any of them would make C++ the schema
  language and block multi-language generation. sqlite_orm is additionally license-incompatible.
- ODB validates the architecture direction (a real compiler, static SQL, generated mapping) but is
  single-language, GPL, and requires its own compiler. It is cited as precedent only.

**ASSUMPTION:** the stable Drizzle introspection surface (`getTableConfig`, `getTableColumns`) is
sufficient to express IR v1 (tables, columns, indexes, FKs, checks, primary keys). Phase 0 must prove this
with a conformance suite; anything missing is handled by an explicit frontend-adapter extension, not by
scraping the TS AST.

## 5. Chosen source-of-truth model

### 5.1 Pipeline

```text
schema.ts + queries/*.ts                  (authoring, Drizzle-shaped; in-tree: orm/drizzle/)
        |
        |  frontend adapter (pinned drizzle-orm@0.45.3)
        v
   IR v1: esdb.ir/v1, sealed canonical JSON     (in-tree: orm/ir/esdb-ir-v1.md)
        |                                        irHash = SHA-256(hash projection)
        |
         |  compiler: tools/esdb-schema/
        +-----------------------+----------------------+
        |                       |                      |
        v                       v                      v
 generated C++             generated TS          generated ES3 + ESABI contract
 repository bindings       types + metadata      named-operation facade/manifest
        |
        |  drizzle-kit@0.31.11 ordinary SQL/snapshots
        v
   package-migrations (normalization + lint + provenance + C++ wrapper)
        v
   esdb_migration[] steps -> esdb_migrate() -> PRAGMA user_version
```

### 5.2 What is authoritative for what

| Artifact | Authority |
|---|---|
| `schema.ts`, `queries/*.ts` | Authoring intent. Human-edited. |
| IR v1 JSON + `integrity.hash` | **Canonical semantics** for codegen, type mapping, verification: the language-neutral contract. Normative contract: `orm/ir/esdb-ir-v1.md`; generated by the frontend, sealed by the compiler, committed, reviewed. The hash covers the canonical semantic projection only; sealed file bytes are not the hash domain. |
| Drizzle Kit `migration.sql` + `snapshot.json` | **DDL of record** for migrations. Generated by the pinned stable CLI (`drizzle-kit@0.31.11`, the sole shipped DDL/diff author), committed, packaged, linted, and validated against IR. |
| Generated C++/TS/ES3 + `manifest.json` | Build products. Regenerable byte-for-byte; never hand-edited. |
| `PRAGMA user_version` | **Runtime ledger.** The only durable applied-version state. |
| Kit journal (`__drizzle_migrations`) | Build-time only. Not used at runtime. |

### 5.3 Why IR is not SQL

IR v1 does **not** store DDL. Kit owns DDL text and is the sole shipped DDL/diff author. IR stores the
semantic schema (tables, columns, logical types, nullability, keys, `UNIQUE` constraints, explicit indexes,
checks, and foreign keys) and named-query plans. IR-native `CREATE TABLE` emission is bootstrap/oracle
tooling only and is never the shipped DDL of record. Baseline-zero migration packaging and physical-schema
tests apply Kit SQL to SQLite and compare the realized schema with the IR-derived physical model. The
read-only physical-schema and adoption commands also compare live databases against recorded expectations.
These checks compare SQLite's realized schema, not formatting-sensitive SQL text; they do not replace Kit
as the DDL/diff author.

### 5.4 Version pinning rules

- `drizzle-orm` is pinned to an exact version (`0.45.3` for v1). Range specifiers are forbidden.
- The frontend adapter lives in its own package (`orm/drizzle/` projected) and is the only module
  allowed to import `drizzle-orm/sqlite-core` and `getTableConfig`/`getTableColumns`.
- `drizzle-kit` is pinned to an exact stable version (`0.31.11`) and invoked **as a CLI only**
  (`generate`, `export`, `check`). Importing `drizzle-kit/api`, `drizzle-kit/cli`, or any v1 SDK surface
  is forbidden until the v1 line is stable.
- Upgrading either pin is a deliberate task that must include a differential IR comparison
  (`irHash` before/after) and a migration-DDL differential.

## 6. IR v1

### 6.1 Shape

IR v1 is normative in `orm/ir/esdb-ir-v1.md` (with an informative JSON Schema mirror at
`orm/ir/esdb-ir-v1.schema.json`) and implemented by `tools/esdb-schema/`. This document does not
redefine it; the summary below is structural only.

```jsonc
{
  "ir_version": "esdb.ir/v1",          // required, exactly this string
  "schema":   { "name": "user", "dialect": "sqlite", "namespace": "esdb.orm.user" },
  "tables":   [ /* name/sql_name, columns, keys, uniques, indexes, checks, foreign_keys */ ],
  "queries":  [ /* select | insert | upsert | update | delete; joins, keyed where, eq only in v1 */ ],
  "integrity":{ "algorithm": "sha256", "canonical": "esdb-canonical-json-v1", "hash": "<hex>" },
  "generator":{ /* non-semantic; must not affect codegen */ },
  "annotations": { /* free-form, non-semantic, excluded from the hash; must not affect codegen */ }
}
```

In-tree v1 scope: four scalar types (`integer`, `text`, `real`, `blob`); primary keys, `UNIQUE`
constraints, explicit indexes, checks, and structural foreign keys; declarative CRUD + upsert queries
with `eq` predicates and INNER/LEFT joins; keyed `where` required for `update`/`delete`; keyed-or-unique
`where` required for `cardinality: "one"` selects; deterministic logical-name vs physical-`sql_name`
mappings; and incremental Kit SQL packaging into contiguous ESDB migration steps. Unknown fields are
rejected. Everything else in this section is either the in-tree contract restated or a marked extension
proposal.

### 6.2 Canonical serialization (hash domain)

Canonical bytes are defined by `esdb-canonical-json-v1` (normative in `orm/ir/esdb-ir-v1.md` §6,
reference implementation in `tools/esdb-schema/src/canonical.mjs`):

1. UTF-8, no BOM, no insignificant whitespace, no trailing newline. This encoding defines the canonical
   bytes; the sealed file is this encoding of the full document (including `integrity`), so sealed file
   bytes are not the hash domain.
2. Object keys sorted ascending by Unicode **code point** (astral keys sort by scalar value, not by
   UTF-16 code unit).
3. Minimal string escaping (`\"`, `\\`, `\b`, `\t`, `\n`, `\f`, `\r`, `\u00xx` for other C0 controls);
   all other code points emitted raw UTF-8; lone surrogates rejected (`IR024`).
4. **JSON numbers are forbidden** (`IR022`). Every numeric datum is a canonical decimal string. This
   removes floating-point formatting from the hash domain entirely.
5. The hash projection is the document with the top-level `integrity`, `generator`, and `annotations`
   keys removed; `irHash = SHA-256(canonical bytes of the projection)`.
6. The embedded form is
   `integrity = { algorithm: "sha256", canonical: "esdb-canonical-json-v1", hash: "<lowercase hex>" }`.
   `seal` computes it; `hash --check` recomputes and fails on mismatch.
7. `generator` and `annotations` are excluded from the hash and are non-semantic. Validation rejects
   semantic, codegen-affecting, or SQL-affecting data carried through them; generator version and options
   that change emitted bytes are recorded in the manifest and artifact headers so their effect is reviewed.

The compiler also records migration-file provenance and SQLite-realized physical schema identities in
manifest v2 and adoption artifacts. These are separate from the normative IR v1 `integrity.hash` domain.
The remaining proposed architecture-level hashes are not part of the in-tree contract:

| Hash | Domain |
|---|---|
| `irHash` | In-tree: canonical bytes of the hash projection. |
| `queryHash(q)` | Canonical query object (extension: per-query identity for catalogs and ES3 plan IDs). |
| `sqlHash(step)` | Implemented migration-manifest provenance: SHA-256 of normalized Kit SQL bytes. |
| `physicalSchemaHash` | Implemented SQLite introspection hash in physical-schema/adoption tooling ([§13.2](#132-canonical-physical-schema-hash)). |
| `chainHash(n)` | `SHA-256(chainHash(n-1) || sqlHash(n) || physicalSchemaHash(n) || irHash)`, with `chainHash(0) = SHA-256("esdb-orm/v1")`. |

`queryHash(q)` and `chainHash(n)` remain proposals and are not consumed by current code. `sqlHash` and
`physicalSchemaHash` are implemented provenance/verification data, not additions to the IR v1 hash seal.

### 6.3 Type system

In-tree IR v1 scalar types (normative):

| IR `type` | SQLite | C++ | TS | ES3 |
|---|---|---|---|---|
| `integer` | INTEGER (signed 64-bit) | `std::int64_t` | `number` with safe-integer policy, or canonical decimal `string` in exact mode | same as TS |
| `text` | TEXT | `std::string` (UTF-8) | `string` | `string` (hex transport across ESABI) |
| `real` | REAL (binary64) | `double` | `number` | `number` |
| `blob` | BLOB | `std::vector<unsigned char>` | uppercase hex `string` | uppercase hex `string` |

Extension types proposed by this architecture (not yet in the in-tree contract; the full cross-language
mapping is in [§12](#12-exact-cross-language-types)): `bool`, `int32`, `date`, `timestamp_ms`, `json`.
Each requires an IR minor revision, frontend mapping, codegen, and tests before use.

Rules (in-tree unless marked):

- Identifiers: IR `name` and `sql_name` both match `[A-Za-z_][A-Za-z0-9_]*`, length 1..64; `sql_name`
  must not be an SQL keyword; emitted double-quoted. The `sqlite_` and `__esdb_` prefixes are rejected
  case-insensitively, and names that collide after case folding or any naming transform (two IR names
  mapping to one emitted SQL name) are rejected before any SQL text is produced (`orm/ir/esdb-ir-v1.md` §3).
- No `ANY` columns. Generated SQL never uses `SELECT *`; the v1 compiler emits the explicit column list
  in declaration order.
- Nullability is per column and explicit. Generated APIs model it; the C++ generated layer is
  C++11-compatible and represents NULL with explicit null state (no `std::optional` requirement).
- Defaults are typed literals; `real` defaults cannot express NaN or infinities. Nullable columns may
  have type-compatible defaults; `NOT NULL DEFAULT NULL` and text defaults containing U+0000 are rejected
  (`IR016`).
- `json` (extension proposal): TEXT + `json_valid()` CHECK. ESDB `ARRAY`/`OBJECT` value tags are Store
  concepts and are never used for relational columns.
- `double`: `NaN` bind rejection and the `±Inf` policy are extension proposals, to be measured on
  SQLite 3.53.4 through ESDB before being locked.
- Collations: `BINARY` (default) and `NOCASE` only; custom collations are out of scope.

### 6.4 Compatibility rules (what changes mean)

| Change | Classification | Migration expectation |
|---|---|---|
| Add nullable column / column with constant default | Additive | One step, safe |
| Add table / index | Additive | One step, safe |
| Add NOT NULL column without default | Breaking for existing rows | Kit will require a data step (`--custom`) |
| Drop column/table, change type, change nullability | Destructive | Requires explicit destructive marker in the step (lint gate) |
| Rename column/table | Destructive unless declared | Renames must be declared to Kit so it emits `ALTER ... RENAME`, not drop+create |
| Change a query definition | Code change | `irHash` changes; no migration (per-query `queryHash` is an extension) |

Renames are never inferred by the ORM. Kit prompts for them at `generate` time; the chosen answer is
recorded in the Kit snapshot and therefore in the packaged migration.

## 7. Migration packaging and mapping to `esdb_migrate`

Scope: production migration packaging is implemented. Drizzle Kit owns migration authoring/history;
`esdb-schema package-migrations` consumes the committed ordinary Kit SQL, normalizes and lints it,
records provenance in manifest format v2, and generates the C++11 `esdb_migration[]` wrapper. ESDB owns
execution, atomicity, rollback, and `PRAGMA user_version`. The IR-derived bootstrap emitter remains an
independent oracle/testing tool and is not production DDL.

### 7.1 Packaging layout

```text
generated/migrations/
  v0001__<kit-slug>.sql
  v0002__<kit-slug>.sql
  ...
  manifest.json
  <schema>_migrations.hpp
```

The implemented manifest v2 shape is:

```jsonc
{
  "formatVersion": "2",
  "irHash": "sha256:...",
  "baseline": "0",
  "targetVersion": "2",
  "normalizerVersion": "lf-v1",
  "physicalSchema": {
    "normalizerVersion": "sqlite-introspection-v1",
    "hash": "sha256:...",
    "basis": "full-kit-chain"
  },
  "kit": {
    "tool": "drizzle-kit-cli",
    "version": "0.31.11",
    "ordering": "lexicographic-relative-path"
  },
  "migrations": [
    {
      "ordinal": "1",
      "fromVersion": "0",
      "toVersion": "1",
      "source": "0000_example.sql",
      "file": "migrations/v0001__example.sql",
      "sqlHash": "sha256:...",
      "snapshotHash": "sha256:...",
      "destructive": false,
      "destructiveAck": false
    }
  ]
}
```

SQL is normalized to LF with exactly one trailing newline before hashing and embedding. Snapshot bytes are
hashed for traceability when a matching Kit snapshot exists; snapshots are not copied into the runtime
package. For a baseline-zero package, the exact normalized Kit chain is also materialized in scratch SQLite
and the resulting SQLite-semantic physical schema hash is recorded with its normalizer identity. For a
nonzero/adopted baseline, the package cannot reconstruct the pre-existing schema from later migrations
alone, so `physicalSchema.hash` is explicitly `null` with
`basis: "external-baseline-required"` rather than fabricating an identity. The generated C++ wrapper
exposes the same resolved/unresolved physical-schema provenance.

Generated C++ (shape):

```cpp
// generated - do not edit
static const char kSqlV1[] = "CREATE TABLE ...;\n";   // static, compiled into the binary
static const char kSqlV2[] = "CREATE INDEX ...;\n";

static esdb_status apply_v1(esdb_database* db, uint32_t, uint32_t, void*, esdb_error* e) {
  return esdb_exec(db, kSqlV1, e);   // never BEGIN/COMMIT here
}
static esdb_status apply_v2(esdb_database* db, uint32_t, uint32_t, void*, esdb_error* e) {
  return esdb_exec(db, kSqlV2, e);
}

static const esdb_migration kMigrations[] = {
  {0u, 1u, apply_v1, nullptr},
  {1u, 2u, apply_v2, nullptr},
};
static const uint32_t kTargetVersion = 2u;

esdb_status esdb_orm_migrate(esdb_database* db, esdb_error* error) {
  return esdb_migrate(db, kTargetVersion, kMigrations, 2u, error);
}
```

### 7.2 Mapping rules

1. Ordinary Kit `.sql` files are discovered recursively and sorted by relative path using a
   locale-independent lexical comparator. Each source file becomes one ESDB step; the original relative
   source path is recorded in the manifest.
2. Each step is exactly one version increment (`from = n-1`, `to = n`), matching `esdb_migrate()`'s
   contiguous single-step requirement.
3. The step callback executes the step's SQL with `esdb_exec()` and nothing else. ESDB owns ordering,
   atomicity, and the `user_version` update. The callback never takes transaction control.
4. The whole chain runs in one `BEGIN IMMEDIATE` transaction. On any failure, everything rolls back and
   `user_version` is unchanged. This is a feature: a partially migrated database cannot exist.
5. `user_version` is the only runtime ledger. The generated `kTargetVersion` must equal the manifest's
   `targetVersion`; a mismatch is a build error.
6. Downgrades are not supported. `esdb_migrate()` rejects them; the ORM never emits downgrade code.
7. Packaged SQL is compiled into the generated migration wrapper as static string constants. Runtime
   migration execution does not depend on external SQL files or the Kit journal.

### 7.3 Baseline adoption (Workmark path)

`TARGET:` a future `esdb-orm adopt --baseline N` workflow should:

1. Introspect the live database and build a canonical physical-schema hash.
2. Compare it against the IR-derived hash for version N. They must match exactly; otherwise adoption fails
   with a structured diff.
3. Require `PRAGMA user_version == N` (or set it once, with an explicit `--set-user-version` operator
   flag, when the product's existing ledger is compatible).
4. Package only steps `N+1..target`. The manifest records `"baseline": N`.
5. The ORM never touches Kit's `__drizzle_migrations` table and never rewrites existing product tables.

This is the only sanctioned path for a product with an existing schema (Workmark being the reference
case). It does not require Store, the adapter, or a rewrite of the product's migration history.

### 7.4 Migration safety lint

Every packaged step must pass, at build time:

- No `BEGIN`, `COMMIT`, `END`, `ROLLBACK`, `SAVEPOINT`, or `RELEASE`; transaction
  control belongs to `esdb_migrate()`.
- No Runtime-owned PRAGMAs: `user_version`, `schema_version`, `journal_mode`, `locking_mode`,
  `synchronous`, `wal_checkpoint`, `writable_schema`, or `foreign_keys`.
- No `ATTACH`, `DETACH`, `VACUUM`, temporary-schema objects, or direct `sqlite_master` /
  `sqlite_schema` access.
- `DROP`, `ALTER`, and `RENAME` classify the migration as destructive. Packaging requires an explicit
  acknowledgement sidecar (`{"acknowledgeDestructive":true}`, optionally scoped to source paths);
  the manifest records both `destructive` and `destructiveAck`.
- Every packaged file is self-contained; runtime execution uses the generated embedded wrapper rather
  than external files.

The lint is deliberately conservative. Expanding the allowed SQL surface requires tests against
`esdb_migrate()` transaction semantics rather than bypassing the policy.

### 7.5 CLI surface

## 8. Generated C++ strategy

### 8.1 Why the escape hatch is the right lane

ESDB Runtime deliberately does not wrap prepared statements. `docs/ABI.md` states that
`esdb_native_handle()` "is intended for product-owned prepared statements and SQLite APIs not wrapped by
Runtime." Generated C++ is exactly that: product-owned, compile-time-known statements. Using the escape
hatch is not a bypass; it is the documented integration point, subject to its rules.

Rules the generated code must obey:

- The `sqlite3*` is borrowed. Never close it, never store it past `esdb_close()`, never use it from a
  thread that may not use the `esdb_database`.
- Use ESDB for transaction control (`esdb_begin`/`esdb_commit`/`esdb_rollback`) and for migrations
  (`esdb_migrate`/`esdb_exec`).
- Never modify reserved `__esdb_` objects, durability pragmas, or extension loading.
- The connection's mutex mode governs access: `FULLMUTEX` permits multi-thread use of the connection, but
  logical transaction sequences still require application serialization. A generated repository/connection
  instance is single-caller-at-a-time unless the application externally serializes; `FULLMUTEX` serializes
  individual SQLite calls and does not make a reset/bind/step (or any statement-cache) sequence atomic.

### 8.2 Baseline and API shape

- Language baseline: C++11-compatible generated code (MSVC 19.44+ is the current Windows toolchain; ESDB
  core is C++11). The generated layer must not require `std::optional` or other C++17-only library types;
  nullable values use explicit null state.
- Dependencies: `<esdb/esdb.h>`, `<esdb/sqlite3.h>`, standard library. `esdb.hpp` is optional.
- Generated per table: a row struct with explicit null state for nullable columns (a `has_*` flag or
  equivalent; C++11-compatible, no `std::optional` requirement); a `Table` type exposing `selectById`,
  `insert`, `update`, `erase`, and the named-query functions.
- Generated per query: a function with a typed parameter struct and a typed result; SQL is a `static
  const char[]`; column indexes are `static constexpr int`; binds are positional and fixed.
- Statement cache: one prepared statement per generated query per repository instance, lazily prepared
  with `sqlite3_prepare_v2`, then reused with `sqlite3_reset` + `sqlite3_clear_bindings`. The prior
  `sqlite3_reset()` step status is intentionally ignored because it was already surfaced by the preceding
  call. The repository borrows `esdb_database*` and must be destroyed before `esdb_close()`.
- Prepare-time self-check: after prepare, assert `sqlite3_bind_parameter_count` and
  `sqlite3_column_count` against the compiled expectations. This catches schema drift even when full
  verification is disabled.
- Row mapping: direct `sqlite3_column_int64/double/text/blob` calls with constant indexes. No dynamic
  value layer, no reflection, no string-keyed lookup. TEXT/BLOB pointers are borrowed from the statement
  and are copied into the row struct before the next `step()`.

### 8.3 Value binding (no exceptions to bind-only)

Binding rules cover in-tree types plus the extension types marked in [§12](#12-exact-cross-language-types).
- `sqlite3_bind_int64`, `sqlite3_bind_double`, `sqlite3_bind_text64(..., SQLITE_UTF8)`,
  `sqlite3_bind_blob64`, `sqlite3_bind_null`.
- `int64` uses the 64-bit lane end-to-end. `int32` is range-checked before binding.
- `bool` binds as 0/1 integer. `date` binds as `YYYY-MM-DD` text. `timestamp_ms` binds as int64.
- `json` binds as UTF-8 text; `json_valid()` is enforced by the column CHECK.
- `NaN` double binding is rejected before reaching SQLite ([§6.3](#63-type-system)).
- No generated code path may call `sqlite3_mprintf` or build SQL with string concatenation. A static
  analysis gate greps generated sources for SQL-construction patterns ([§15](#15-security-and-sql-injection-posture)).

### 8.4 Transactions

- The application owns transaction scope. Generated helpers do not open implicit transactions.
- Batch helpers (`insertMany`, `applyMany`) take an existing transaction or run inside an explicit
  `esdb_begin`/`esdb_commit` scope supplied by the caller, so per-row autocommit (and per-row fsync) is
  never hidden inside generated code.
- `esdb_orm_verify()` and migrations use their own ESDB-owned scopes.

### 8.5 Example (shape only)

```cpp
struct Document {
  int64_t id{};
  std::string title;
  bool has_body{};              // explicit null state (C++11)
  std::string body;
  int64_t createdAtMs{};
  bool has_tagsJson{};
  std::string tagsJson;
};

class Documents {
 public:
  explicit Documents(esdb_database* db) : conn_(db) {}

  esdb_status GetById(int64_t id, bool* outFound, Document* out, esdb_error* e);
  esdb_status Insert(const Document& row, int64_t* outId, esdb_error* e);
  esdb_status ListByCreated(int64_t limit, int64_t afterId, std::vector<Document>* out, esdb_error* e);
  esdb_status UpdateTitle(int64_t id, const std::string& title, int64_t* outChanged, esdb_error* e);
  esdb_status DeleteById(int64_t id, int64_t* outDeleted, esdb_error* e);

 private:
  OrmConnection conn_;  // statement cache; borrowed esdb_database*
};
```

## 9. Generated ES3 / ESABI strategy (named ORM operations; generic SQL is separate)

### 9.1 Invariant

Generated ORM ES3 remains a fixed named-operation surface even though generic ESDB now has a typed-SQL
escape hatch. Therefore:

- Generated ORM requests carry **operation names and typed values, not SQL text**. One compiled native
  function exists per named query with fixed arity and canonical value transport.
- Generic `Database.query(sql, parameters, options)` / `run(sql, parameters)` is an explicit
  application-query capability outside generated ORM v1. Its SQL text and P1 typed parameter packet are
  separate ABI arguments; caller values are bound by Runtime and never interpolated.
- Generated ES3 never owns production DDL. A native product bridge applies the generated migration
  wrapper during database-open lifecycle, as the User reference bridge does. Advanced generic SQL can
  technically execute SQLite DDL, but production schema authority remains Drizzle Kit/migration-owned.
- Both paths reuse ESDB's byte-exact wire conventions (hex for byte-exact strings/blobs and SQL UTF-8,
  canonical decimal strings for exact 64-bit values, exact decimal encoding for encoded DOUBLE values).
- No asynchronous callbacks. Generated queries are synchronous; scans are bounded and paged. Generic
  SQL is also synchronous and caps returned rows/wire bytes at the adapter boundary.

### 9.2 v1 mechanism: generated contract + product bridge

The implemented generated-ORM lane gives ES3 typed relational access without using the generic SQL escape hatch:

1. The compiler generates the ES3 facade, a named-operation ESABI contract header, a canonical bridge
   manifest, and a compilable reference stub. The contract fixes operation names, arity, lane types,
   nullability, IR identity, and U1 reply grammar.
2. A product implements those generated operations in its native bridge on top of the generated C++
   repository and migration wrapper. `examples/orm/user/bridge/user_orm_bridge.cpp` is the concrete
   reference implementation and builds as `UserOrmBridge.dll` when ESABI is available.
3. ES3 callers pass canonical values; the native bridge validates/decodes them and invokes generated
   repository methods. Plan identity is the exported named function itself; there is no runtime plan
   registry to validate and no SQL text on the wire.

Costs: each generated-ORM ES3 consumer ships a small DLL. That matches the existing topology (Workmark
already keeps native storage in a helper; ESPACK already ships self-extracting ExternalObject bundles).
Benefits: generated ORM hot paths still have zero SQL text on their wire, no query interpreter/VM, and the
existing ESABI hardening (generation-tagged handles, thread-local staging, guarded unload) applies
unchanged. Generic typed SQL remains available separately when a fixed generated operation is not the
right abstraction.

### 9.3 Deferred alternative: validated plan registry

`PROVISIONAL:` a future ESDB adapter revision could host a generic plan registry: the ORM ships a plan
manifest (plan IDs, arity, types, schema fingerprint) and the adapter accepts only plans whose IDs resolve
in the manifest compiled into the adapter. This is a larger ESDB ABI change and an interpreter to test;
it is explicitly deferred until the generated-adapter lane has proven the semantics. If it ever lands, the
same generated-ORM invariant holds: that plan-registry wire would carry plan IDs and values, not SQL.
This does not remove the separate generic typed-SQL escape hatch.

### 9.4 ES3 lifecycle rules

- `ESDB.unload()` semantics and the "DLL stays mapped until process exit" host behavior are inherited; the
  generated facade must not assume hot-reload.
- Adapter database handles are generation-tagged; the generated facade treats stale-handle rejection as a
  normal error path.
- One adapter slot may own one explicit transaction; the generated facade exposes `transaction(callback)`
  over the canonical native transaction, not an emulated one.
- Scans return bounded pages (`limit` + `after` cursor) to keep the Illustrator UI responsive; a full-table
  scan is never implicit.
- Static and live parse gates use the shared ESTC pipeline before any ES3 artifact ships.

## 10. Modern TS strategy (Kysely adapter)

Kysely is not the schema authority, but it is the best available *runtime* query builder for modern TS
(public `Dialect`/`Driver` interfaces, MIT, `0.29.6`). The TS lane is therefore split:

1. **Generated types** from IR: one interface per table (`Document`), one parameter/result type per named
   query, and a `Database` interface shaped for Kysely (`DB['documents']`).
2. **Named query functions** generated as thin wrappers that either execute the same compiled SQL through
   a Kysely `sql` template with positional binds, or call a driver directly. The generated SQL is the
   single source of DML; Kysely must not recompile or rewrite it.
3. **Kysely `Dialect`/`Driver` adapter** (later phase) that targets ESDB. Two options:
   - In-process: a driver that calls into the ESDB adapter/helper through the product's native bridge.
   - Helper-process: a driver over the product's IPC transport (the Workmark pattern), where the helper
     owns the `esdb_database` and the TS side owns queries.
4. **Exactness requirement:** the driver must be configured for exact 64-bit integers
   (e.g. `safeIntegers`-style driver options) and for UTF-8-safe text/blob transfer. A conformance test
   must prove `int64 > 2^53`, embedded NUL in text/blob, and astral text round-trips. Node >= 22 is
   acceptable for tooling/helper processes; it is irrelevant to Illustrator's ES3 runtime.
5. **Scope rule:** ad-hoc Kysely queries are allowed only in tooling and helper processes, never as the
   canonical application data path. Canonical paths use generated named queries so C++, TS, and ES3 share
   one SQL corpus.

## 11. Named query model

The in-tree IR v1 defines the query surface normatively (`orm/ir/esdb-ir-v1.md` §5): kinds
`select|insert|upsert|update|delete`; `eq` predicates only; explicit INNER/LEFT joins; keyed `where`
for `update`/`delete`; keyed-or-unique `where` required for `cardinality: "one"`; insert/upsert must
supply every NOT NULL column without a default; parameter order is derived, never stored. This section adds the architecture around that surface; it
does not replace it.

API argument order and SQL bind order are separate concerns: SQL binds are the fixed positional sequence
bound into the statement, while the ergonomic API order (for example key-first for `update`) is chosen by
the generator. For `update`, SQL binds are the SET assignments followed by the WHERE predicate. Wrappers
map API arguments onto the bind order; both orders are compile-time constants.

### 11.1 Declaration

Queries are declared in `queries/*.ts` as typed specs against the schema types:

- **Structured specs** for the common shapes: `select` (projection, filters, order, limit/cursor),
  `insert`, `update`, `delete`, `count`, `upsert`. The compiler validates column references and types
  against IR and emits canonical SQL.
- **Static SQL specs** (deferred): a compile-time SQL string with named parameters for shapes the
  declarative model cannot express. Rules if adopted: compile-time only, no runtime string assembly, no
  interpolation of values (binds only), hashed and reviewed like any other generated artifact, and
  recorded in the query catalog. The in-tree generated-query contract deliberately has no caller-built
  dynamic SQL. This is distinct from generic ESDB Runtime/ExternalObject `esdb_query` /
  `Database.query`, which is an explicit typed application-query escape hatch outside IR v1.

### 11.2 Compilation

For each query the compiler currently emits:

- canonical SQL with positional binds;
- a canonical SQL bind order and result column order;
- a separate ergonomic API parameter order that may differ from bind order (for example, key-first
  UPDATE APIs map to SET-first SQLite placeholders);
- a generated C++ method, TypeScript metadata, ES3 repository method, and ESABI bridge operation.

`queryHash` is a future catalog extension; v1 identity is currently anchored by the sealed whole-IR hash.

### 11.3 Policies

- **No dynamic SQL at runtime.** Optional filters are separate named queries (compile-time variants). A
  dynamic-predicate API is explicitly out of scope for v1.
- **No `SELECT *`.** Projection is explicit; column indexes are compile-time constants.
- **No lazy relations.** Joins are explicit named queries; related data is fetched by explicit calls.
  There is no object graph identity map.
- **Pagination:** keyset (`after` cursor) is the default for list queries; `OFFSET` is allowed but
  discouraged in review.
- **Result cardinality:** `one`, `many`, `changes` (in-tree); `count` and nullable-select variants are
  extension proposals, explicit per query and typed per language.
- **Bridge catalog:** `bridge/<schema>_orm_bridge.json` lists generated named operations, kinds,
  cardinalities, API parameters, bind parameters, signatures, return shapes, wire version, and the whole
  IR hash. Per-query hashes are a future extension.

## 12. Exact cross-language types

### 12.1 In-tree contract (normative)

| IR `type` | SQLite | C++ | TS | ES3 |
|---|---|---|---|---|
| `integer` | INTEGER, signed 64-bit | `std::int64_t` | accept `number` (safe integer) or canonical decimal `string`; return `number`, throw `RangeError` outside ±(2^53−1) unless exact mode is requested (then canonical decimal strings) | same policy as TS; wire is always a canonical decimal string |
| `text` | TEXT | `std::string` (UTF-8) | `string` | `string`, ASCII-hex across ESABI |
| `real` | REAL (binary64) | `double` | `number` | `number` |
| `blob` | BLOB | `std::vector<unsigned char>` | uppercase hex `string` | uppercase hex `string` |

Wire rule (in-tree): every integer parameter and result is a canonical decimal string
(`-?(0|[1-9][0-9]*)`, `-0` normalized to `0`, bounded to `[-2^63, 2^63-1]`), even when the script-visible
value is a `number`. Exact `int64` therefore survives TS, ES3, and the ABI even though neither language
represents it natively.

Strict policy (normative): NULL is distinct from `''`, `0`, and zero-length BLOB and round-trips as NULL;
`int64` is exact and never silently rounded; text is valid UTF-8 (invalid sequences are rejected, never
repaired); BLOBs are byte-exact and never reinterpreted as text; and no value is coerced across types on
read or write. The canonical wire encoding above is the only transport policy: no second encoding is
introduced anywhere in the stack.

### 12.2 Extension types (proposed)

| Logical | SQLite | CHECK / enforcement | C++ (C++11) | TS | ES3 (via adapter) |
|---|---|---|---|---|---|
| `bool` | INTEGER | `IN (0,1)` | `bool` | `boolean` | `boolean` |
| `int32` | INTEGER | range CHECK | `int32_t` | `number` (checked) | `number` |
| `date` | TEXT | `YYYY-MM-DD` shape + validity | `OrmDate` (y/m/d) | `string` | `string` |
| `timestamp_ms` | INTEGER | int64 range | `int64_t` + `TimestampMs` newtype | safe-range `number` or decimal string per the in-tree policy | decimal string |
| `json` | TEXT | `json_valid()` | `std::string` (canonical UTF-8) | typed generic + explicit codec | `string` + ESON codec |
| nullable `T` | as `T` | - | explicit null state (C++11; no `std::optional` requirement) | `T \| null` | `null` or `T` |

Explicit decisions:

- **int64 is never silently rounded.** The in-tree policy (safe-range `number`, `RangeError` on overflow,
  exact decimal-string mode, decimal-string wire) is the contract. `bigint` was considered and is a
  possible future addition, not a v1 change.
- **blob is byte-exact; TS/ES3 use uppercase hex strings** per the in-tree contract and the measured
  Adobe string-lane limits. A TS-side `Uint8Array` convenience wrapper is a possible later addition, not
  part of the IR contract.
- **date is a civil date string.** `YYYY-MM-DD`, no timezone, no epoch conversion, stock-tool readable.
- **timestamp is epoch milliseconds UTC in int64.** Sortable, exact, no locale or timezone ambiguity.
  Timezone conversion is an application concern at the edge.
- **bool is 0/1 with a CHECK**, not a text `"true"/"false"`.
- **json is canonical UTF-8 text with a `json_valid()` CHECK.** The ORM does not parse or re-serialize
  JSON; the peer codec (ESON in ES3, a strict codec in TS/C++) owns syntax and canonicalization. ESDB
  `ARRAY`/`OBJECT` value tags are not used.
- **double NaN binding is rejected, ±Inf allowed.** `PROVISIONAL` pending measurement of SQLite 3.53.4
  behavior through the escape hatch.
- **TS `Date` is never generated.** It is lossy for the epoch-ms lane and timezone-ambiguous;
  applications may convert explicitly at their edges.

`PROVISIONAL:` the C++ newtype wrappers (`OrmDate`, `TimestampMs`) and TS brands are convenience choices;
if they cause friction they are replaced by plain `std::string`/`int64_t`/`number` without changing IR
or the wire contract.

## 13. Schema mismatch detection

Build and adoption verification compare the sealed IR semantics with separately canonicalized SQLite
physical-schema evidence; these hashes have distinct domains.

### 13.1 Build-time and adoption verification

Implemented in-tree:

- `integrity.hash` seal mismatch (`hash --check`) fails the build; IR validation (identifiers, types,
  generated-name hazards, query shapes/order) runs before SQL/code is emitted.
- The User drift gate re-extracts/seals IR from `schema.ts` and byte-compares it with the committed sealed
  IR, so frontend/schema drift fails validation.
- `generate --check` strictly verifies the generated model artifact set byte-for-byte.
- `package-migrations --check` re-normalizes committed Kit SQL, recomputes SQL/snapshot provenance, and
  strictly verifies manifest v2 plus the generated migration wrapper.
- Baseline-zero Kit migrations are applied to scratch SQLite databases and compared with the IR-derived
  physical model. `physical-hash` and `physical-diff` inspect SQLite's realized schema; adoption baseline
  and report commands are read-only against the supplied database.
- CI runs the compiler/drift checks and compiles generated C++/ESABI surfaces as C++11.

### 13.2 Canonical physical-schema hash

`physicalSchemaHash` is implemented by `tools/esdb-schema/src/physical-schema.mjs`. It is based on
SQLite's realized schema, not migration SQL formatting. The canonical form preserves structured table,
index, and foreign-key semantics and conservatively retains normalized CREATE-token semantics where
SQLite PRAGMAs do not expose enough detail (including CHECK expressions). Tables and objects are sorted
deterministically; the canonical form is hashed with SHA-256 and the normalizer identity/version is
recorded in manifests and adoption reports.

For a nonzero/adopted baseline, later migration files cannot reconstruct the pre-existing physical schema.
The manifest therefore records an unresolved external-baseline provenance instead of fabricating a hash;
the read-only adoption report compares the supplied live schema and version explicitly.

### 13.3 Runtime verification

A generated native `esdb_orm_verify(db, mode, &report)` helper remains a target. The in-tree tooling
provides read-only physical-hash/diff and adoption commands; it does not claim that the C++ runtime
currently verifies physical schema automatically at open.

| Mode | Checks |
|---|---|
| `off` | none (escape hatch for performance-critical opens) |
| `version` | `PRAGMA user_version == kTargetVersion` |
| `hash` | `version` + `physicalSchemaHash(live) == kExpectedPhysicalSchemaHash` |
| `hash+fk` | `hash` + `PRAGMA foreign_key_check` |

Any future native verification helper may offer version, physical-hash, and foreign-key-check modes. A
client↔bridge handshake that agrees on the compiled IR hash and `user_version` is a contract/version check
only; it is **not** physical-schema verification.

Policy (default `PROVISIONAL`):

- Missing/changed table or column, type mismatch, nullability mismatch, PK/FK/index mismatch: **fail** with
  a structured diff and an `ESDB_ERR_MIGRATION`-class status.
- Extra columns/indexes not in IR: **warn** by default; configurable to fail.
- Reserved-prefix collisions (`__esdb_*` product tables): **fail**.
- `PRAGMA foreign_keys` not matching the IR requirement: **fail** (configuration error), unless explicitly
  waived.

Verification reads run inside a deferred read transaction for a coherent snapshot; if the caller already
holds a transaction, verification participates in it instead of nesting. Verification never writes.

## 14. Performance model

### 14.1 Design levers

- **Prepare once.** One prepared statement per query per connection; `SQLITE_PREPARE_PERSISTENT`; reset +
  clear bindings between uses.
- **No runtime type mapping.** Constant column indexes; direct column reads; no string-keyed dispatch.
- **No hidden transactions.** Callers own scope; batch helpers require an explicit transaction.
- **No hidden queries.** No lazy loading, no N+1, no automatic relation fetching.
- **Zero-copy where safe.** TEXT/BLOB are borrowed from the statement and copied only when they escape the
  step loop.
- **Bounded scans.** Keyset pagination and explicit limits keep memory predictable in-process.
- **ES3 cost awareness.** The hex transport and one ABI call per query dominate; ES3 named queries must
  return whole result sets per call (no per-row round trips) and stay within page bounds.

### 14.2 Budgets and methodology

The release budgets remain `PROVISIONAL` until they have broader machine/host evidence, but the
User reference slice is now measured with the preserved native harness in `bench/` and the ESABI/live
Illustrator benchmark in `examples/orm/user/bridge_bench.cpp` + `tools/live-orm-user-bench.ps1`.
Methodology:

- Same machine, same compiler flags, same ESDB build, warm caches.

## 15. Security and SQL-injection posture

1. **Bind-only values.** Every value reaches SQLite through `sqlite3_bind_*`. There is no generated API
   that accepts SQL fragments, table names, column names, or ordering as parameters.
2. **Compile-time identifiers.** Identifiers come from IR, are restricted to
   `[A-Za-z_][A-Za-z0-9_]*`, and are quoted with double quotes at generation time. Values are never
   quoted into SQL.
3. **No runtime SQL assembly.** Generated code contains static SQL only. A static-analysis gate fails the
   build if generated sources contain `sqlite3_mprintf`, `sqlite3_vmprintf`, or SQL keyword concatenation
   patterns.
4. **Generated ORM ABI is named-operation only.** Generated ES3 ORM calls carry operation names and
   typed values, not SQL text. Separately, ESDB implements an explicit raw-SQL ESABI application-query
   surface outside the generated ORM. It carries SQL text separately from a typed parameter vector, binds
   every caller value, and never interpolates values.
5. **Static SQL query specs remain compile-time.** A future ORM `rawSql` query spec would accept a literal
   source string, hash it into the manifest, and review it in diffs. That compile-time feature is distinct
   from the separately permitted Runtime/ESABI raw-SQL escape hatch.
6. **`SQLITE_DQS=0`.** Double-quoted string literals are not accepted as strings. Generated SQL must use
   single quotes for literals and double quotes for identifiers; a lint enforces this.
7. **Reserved prefixes.** Generated schema validation rejects `sqlite_*` and `__esdb_*` (case-insensitive)
   identifiers, protecting ESDB's internal objects.
8. **Durability policy is not ORM-editable.** Migration lint rejects pragma changes; generated code never
   changes `journal_mode`, `synchronous`, or `foreign_keys` configuration.
9. **Untrusted database files.** Row reads validate ranges (int32, timestamp), UTF-8, and `json_valid()`
   expectations; violations surface as typed errors, never silent coercion. Corrupt databases fail
   verification.
10. **Artifact provenance.** All inputs are version-pinned; all outputs are hashed; generated artifacts are
    reviewed like source. No secrets, absolute paths, or machine-specific data are emitted.
11. **Extension loading stays off.** Generated code must not call `sqlite3_load_extension` or enable
    `load_extension()`.

## 16. Deterministic generation

Determinism is a correctness property, not a convenience: it is what makes generated code reviewable and
what makes `irHash` meaningful.

Rules:

- Canonical IR bytes are defined in [§6.2](#62-canonical-serialization-hash-domain).
- Generators are pure functions of `(IR, generator version, options)`. No timestamps, random values,
  environment variables, absolute paths, locale-dependent formatting, or hash-map iteration order.
- All output files use LF and UTF-8, with a generated header containing the generator version and
  `irHash` only.
- Output file order and internal ordering are explicit (tables by name, queries by name, columns by cid).
- Kit SQL is normalized to LF with exactly one trailing newline; runtime package filenames are derived
  from contiguous ESDB versions plus deterministic source slugs. The manifest records the original relative
  Kit source path and source/snapshot hashes for traceability.
- CI regenerates model artifacts from the committed sealed IR and fails on any byte difference. The User
  drift gate separately re-extracts/seals IR from `schema.ts` and byte-compares it with the committed IR.
- The generator version is recorded in generated artifact headers. By in-tree contract, `generator` is
  excluded from the IR hash projection, so generator upgrades do not change `irHash`; they do change
  generated bytes and therefore require a regeneration commit and review.
- Codegen may read only the hashed projection plus explicitly non-semantic generator version/options;
  semantic or SQL-affecting data must never hide in `generator`/`annotations` (rejected at validation).

## 18. Provisional vs locked registry

### Locked (changing these requires a superseding document)

- Compiler-oriented architecture: no runtime ORM, no reflection, no runtime SQL assembly.
- IR v1 as contracted in `orm/ir/esdb-ir-v1.md` (document shape, identifiers, canonical JSON, hash projection).
- Drizzle ORM `0.45.3` behind a version-pinned adapter; drizzle-kit `0.31.11` CLI-only; no
  `drizzle-kit/api` or v1 SDK dependency until stable.
- `drizzle-kit@0.31.11` is the sole shipped DDL/diff author: ordinary Kit SQL is what gets packaged.
  IR-native `CREATE TABLE` emission is bootstrap/oracle only and is never shipped as the DDL of record.
- IR is the language-neutral semantic/codegen source of truth. `integrity.hash` covers the canonical
  semantic projection excluding `integrity`, `generator`, and `annotations`; sealed file bytes are not the
  hash domain, and codegen-affecting data may not hide in the excluded fields. Kit SQL is the DDL of
  record and is validated against IR.
- Kit migration SQL files map one-to-one to contiguous `esdb_migrate()` steps; `user_version` is the
  only runtime ledger; forward-only; no transaction control in step callbacks; `__drizzle_migrations` is
  never read at runtime. Manifest v2 records the source/order/hash/acknowledgement provenance.
- Generated C++ is C++11-compatible with explicit null state (no `std::optional` requirement) and uses
  the `esdb_native_handle()` escape hatch under its documented lifetime rules. A generated
  repository/connection instance is single-caller-at-a-time unless externally serialized; `FULLMUTEX` does
  not make reset/bind/step atomic.
- Generated ORM ES3 uses real named ESABI operations and never migrates. The separate bounded typed
  raw-SQL ESABI escape hatch is implemented outside generated ORM v1: SQL text and typed values are
  separate and caller values are bound, never interpolated.
- Bind-only values; compile-time identifiers; identifier grammar; reserved-prefix (`sqlite_`, `__esdb_`)
  and case/naming-transform collision rejection.
- Strict value policy: exact `int64` in C++; safe-range `number` or canonical decimal string in TS/ES3;
  decimal-string wire; NULL distinct from `''`/`0`/empty blob; UTF-8 validated; blob byte-exact; no
  cross-type coercion.
- Extension type contract for `bool`, `int32`, `date`, `timestamp_ms`, `json` as proposed in
  [§12](#12-exact-cross-language-types).
- ORM never uses Store and ORM is not Store (no emulation of named stores, revisions, or change
  polling); Workmark remains Runtime-only; baseline adoption is supported.
- Deterministic regeneration is a CI gate.
- API argument order and SQL bind order are separate compile-time concerns; UPDATE SQL binds are SET then
  WHERE, while the ergonomic API may present the key first.

### Provisional (expected to change with evidence)

- A generic validated-plan registry as an alternative to the implemented generated-contract/product-bridge
  ES3 mechanism. Generated ORM remains named-operation based; the separate typed raw-SQL ESABI escape
  hatch is already implemented.
- A C++ convenience helper for runtime physical-schema verification. `physicalSchemaHash`, read-only live
  DB differential, explicit adoption baselines/reports, incremental Kit packaging, manifest v2, `sqlHash`,
  destructive acknowledgement, and migration lint are already implemented behavior.
- Extension types (`bool`, `int32`, `date`, `timestamp_ms`, `json`). FK/CHECK/index generation is implemented.
- STRICT tables: not required in v1; revisit once the Kit differential and adoption paths are proven.
- Date/timestamp representation details (`OrmDate`, `TimestampMs` wrappers) and NaN handling specifics.
- JSON canonicalization policy and codec boundaries.
- Verification default mode and the extra-column policy.
- Final cross-machine performance thresholds and the generated-code-size release budget. The current
  native benchmark measures all three latency classes, but scan results are unstable on shared Windows
  hosts and are reported as inconclusive when the spread limit is exceeded.
- Further migration-lint policy decisions such as explicit `REINDEX`/`ANALYZE` treatment.
- IR-native `CREATE TABLE` emitter details (bootstrap/oracle tooling only; Kit remains the sole shipped
  DDL/diff author).
